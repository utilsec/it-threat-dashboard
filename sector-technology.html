Top Story

Dropbox says about 5,000 accounts were opened without a password — the flaw was in Lenovo’s email verification, and Dropbox’s decision to trust it

Dropbox disclosed on 2 September 2026 that an attacker reached roughly 5,000 customer accounts between 4 and 21 August without ever knowing a password. The weakness sat in a federated login path rather than in Dropbox’s own authentication: a flaw in Lenovo’s email verification process let the attacker register Lenovo IDs against email addresses they did not control, and Dropbox’s identity-linking logic then accepted that Lenovo assertion as proof of ownership without asking for the existing Dropbox password. Sign in with Lenovo ID, and the account opened. Content in some of the affected accounts was viewed and downloaded. Dropbox expired every session established through a Lenovo ID and now requires the Dropbox account password before a Lenovo ID can be used to authenticate; Lenovo described the problem as a legacy integration issue and said its own customers were not affected. The mitigating detail is instructive: accounts with two-factor authentication enabled came through largely intact, because the second factor sat outside the trust that was broken. This leads the sector because nothing here was exotic. Two reputable vendors wired their identity systems together, one side’s verification turned out to be weaker than the other side assumed, and the gap between those assumptions was a working account-takeover path for seventeen days. Any SaaS product that lets a user link a third-party identity to an existing account — which is most of them — owns the same question about every provider it federates with.

Treat “email verified” claims from federated partners as an assertion of their verification quality, not yours, and document what you would do if a partner’s verification were found to be broken.

Critical Incident

Stolen Claude session cookies walk straight past two-factor — and can inherit connectors into corporate Gmail that no AI-platform admin can revoke

Anthropic began emailing affected users in early September 2026 after detecting a threat actor using commodity infostealer malware to lift Claude login sessions from users’ own computers and replay them to access accounts and burn through usage. The mechanism is deliberately boring and that is the point: a session cookie is evidence that a login already happened, so replaying one skips the password and the second factor entirely. Reporting attributes the harvesting to well-known stealer families including Vidar, LummaC2, StealC, RedLine and Acreed on Windows and Atomic Stealer on macOS — none of them specific to AI platforms. Anthropic signed affected users out of all sessions, removed saved payment methods, identified and refunded unauthorised charges, and told users the malware was not related to Claude or installed through it. The consequence enterprises should sit with is the second-order one. A hijacked session inherits every permission the account holds, and where an individual has connected a personal AI account to corporate Google Workspace or Microsoft 365, that includes read access to a work mailbox and Drive. Those OAuth grants live in an administrative gap: the AI vendor can kill the session, but a Workspace or Microsoft 365 administrator often does not know the grant exists, and killing the session does not revoke it.

Attackers are minting their own admin tokens in JFrog Artifactory — the flaw is an authentication bypass, and it is now in CISA KEV

JFrog patched CVE-2026-82329 on 28 August 2026, an improper-authentication flaw in self-hosted Artifactory carrying a CVSS score of 9.8. Under a default configuration, an unauthenticated attacker with network access can obtain administrative privileges; JFrog’s CTO has been explicit that this is improper authentication rather than remote code execution, which matters for how you hunt it. On 1 September watchTowr reported in-the-wild exploitation observed across its honeypot network, with attackers minting administrator tokens and then enumerating users, groups, credential sets and federated access topologies — reconnaissance aimed squarely at what an artifact repository knows about the rest of your estate. CISA added the CVE to the Known Exploited Vulnerabilities catalog on 2 September, and separate reporting describes the flaw being weaponised to deploy reverse shells. Fixed builds are 7.111.21, 7.117.28, 7.125.20, 7.133.29, 7.146.38 and 7.161.20; JFrog’s cloud instances were already patched, so the exposure is self-hosted. Artifactory sits in the middle of the build chain for a great many software vendors, holding registry credentials, signing material and the packages that ship to customers, which is why a token-minting bug there is a supply-chain problem rather than an application one.

Langflow and Rails flaws are being exploited to hunt for OpenAI and AWS keys, with detections climbing from 50 to 360 in days

Two critical flaws in widely used developer platforms came under active exploitation in the closing days of August 2026. CVE-2026-0768 in Langflow, the low-code framework for building LLM workflows, carries a CVSS score of 9.8 and stems from missing validation of user-supplied input, allowing arbitrary Python execution as root. CVE-2026-66066 in Ruby on Rails — nicknamed KindaRails2Shell — is scored 9.5 and lets an unauthenticated attacker read arbitrary files, extract secrets such as API tokens, database credentials and AWS keys, and reach code execution through crafted image uploads that exploit discrepancies between Active Storage and libvips. Telemetry cited in the reporting recorded more than 50 detections within hours on 30 August and roughly 360 by early September, with source traffic for the Langflow attempts concentrated in Russia and one French IP address establishing command-and-control to Israel for the Rails flaw. What the attackers went looking for is the sector-specific detail: environment variables holding OPENAI_API and AWS credentials, plus .ssh access and .bash_history. Related campaigns against older Langflow-adjacent flaws have produced credential harvesters, crypto miners and botnet enrolment. More than 7,100 internet-exposed Rails instances were counted in early August.

A single unauthenticated GraphQL request can rewrite or delete public GitLab projects — and it was being tried three days after the fix

GitLab patched CVE-2026-19478 on 17 August 2026, a code-injection flaw in the GraphQL API scored 9.4. It allows an unauthenticated attacker to modify or delete public projects and user data, including forging merge records and deleting repositories, with no credentials at all. Fixed releases are GitLab Community and Enterprise Edition 19.2.4, 19.1.6, 19.0.8 and 18.11.11; affected branches are 19.2.x, 19.1.x, 19.0.x and 18.11.x prior to those builds. watchTowr’s honeypot network recorded the first in-the-wild exploitation attempts on 20 August, three days after disclosure — a gap that no manual change-approval process is going to win. Where patching cannot happen immediately, GitLab’s guidance points at restricting unauthenticated access to the /api/graphql endpoint or removing public repository access, and defenders can search logs for requests containing the @gl_introduced directive.

High Research

Unit 42 investigated an intrusion that took under ten hours end to end — agentic AI did the work, and no zero-day was needed

Palo Alto Networks Unit 42 published on 2 September 2026 an investigation into an enterprise intrusion driven by frontier AI models and attack-specific agentic frameworks. The operator issued LLM calls to parallel agents that coordinated through structured Markdown files and custom generated scripts, and the full chain — from a publicly reachable web service to control of the victim’s own AI infrastructure — ran in under ten hours, compressing what Unit 42 estimates would normally take a human team around two weeks. More than fifty MITRE ATT&CK techniques appeared across the operation. The finding that should shape planning is what was absent: no novel zero-day was required. The agents mapped an internal microservices architecture, pulled hardcoded credentials out of repositories, harvested administrative credentials from a secrets management system, hijacked CI/CD pipelines to exfiltrate cloud access keys, and then turned the victim’s AI infrastructure to post-compromise use. It also produced an eighty-page audit documenting the weaknesses it exploited. Every step was an ordinary misconfiguration or credential-hygiene failure of the kind most technology organisations already know they have; what changed is that the time available to notice and interrupt them has collapsed from days to hours.

Aurora ransomware operators ran Cursor’s AI agent as their hands-on-keyboard tool, then encrypted ESXi

Independent analyses published in late August 2026 by Gambit Security and CloudSEK describe the Aurora ransomware operation using Cursor Agent — an agentic coding assistant — to conduct hands-on exploitation. Given credentials or network access, the agent was directed to install and configure VPN clients, scan networks with Nmap and NetExec, enumerate domains to assess user privileges, run NTLM relay attacks with PetitPotam and Impacket, and carry out certificate attacks with Certipy. CloudSEK notes the operator planned attacks in Russian through the assistant while deliberately excluding Commonwealth of Independent States networks and domains. Gambit observed hands-on exploitation across ten cases between 8 April and 21 May 2026; CloudSEK’s wider view covers activity from April to July against more than twenty organisations in nine countries, with named victims including Christeyns, Teckentrup, the Helideck Certification Agency and Bayou Title. The payloads are compiled from a single Zig codebase for both Windows and Linux, and the ESXi variant forcibly terminates every virtual machine before encrypting. Initial access documented in the reporting includes email bombing paired with phone calls impersonating IT support to obtain remote access via Xray-core.

Chrome ships an emergency V8 fix for the sixth zero-day exploited in 2026 — and Google is holding the details back

Google released an emergency Chrome update on 3–4 September 2026 for CVE-2026-85046, a type-confusion flaw in the V8 JavaScript and WebAssembly engine that was already being exploited when the fix shipped. The technical root cause is described as arrays with PACKED_ELEMENTS receiving incompatible maps, producing memory corruption that can lead to code execution inside Chrome’s sandboxed renderer; full system compromise would still require chaining a sandbox escape. Fixed builds are 152.0.7977.82/.83 on Windows and macOS and 152.0.7977.82 on Linux. The flaw was reported on 4 August 2026 by researcher Salvatore Gulizia, who uses the handle Serotav, and it is the sixth actively exploited Chrome vulnerability patched this year, following issues in V8, CSSFontFeatureValuesMap, the Skia graphics library and the Dawn WebGPU implementation between February and August. Google has restricted access to the Chromium bug report until most users have the patch and has published no proof of concept or campaign indicators, which is standard practice but does mean defenders cannot hunt for this specifically. Chromium-derived browsers — Edge, Brave, Vivaldi, Opera and Electron applications — inherit the flaw and need their own updates.

Kestra workflow orchestration carries a CVSS 10.0 command-injection flaw, and attackers are using it for reverse shells and coin miners

CVE-2026-49869 in Kestra OSS, the open-source workflow orchestration platform, is scored CVSS 10.0 and was added to CISA’s Known Exploited Vulnerabilities catalog on 2 September 2026. The flaw is an operating-system command injection that lets an unauthenticated remote attacker create and execute arbitrary workflows — in other words, the product’s intended function, reachable without a login. Observed exploitation includes establishing reverse shells, deploying cryptocurrency miners and harvesting data, which is the familiar opportunistic pattern that follows any perfect-score flaw in a service people leave exposed. The reason this belongs on a technology page rather than a general advisory list is where Kestra sits: orchestration platforms hold the credentials for everything they orchestrate. A Kestra instance typically carries database connection strings, cloud service account keys, API tokens for internal services and schedules that reach into production — so command execution on the orchestrator is rarely contained to the orchestrator. Instances are also frequently deployed by data or platform teams on internal assumptions and then made reachable for convenience, which is exactly the exposure profile attackers are scanning for.

LiteLLM’s MCP endpoint accepts any bearer token you care to invent — and honeypots are already seeing it probed

CVE-2026-59822 is an improper-authentication flaw in the Model Context Protocol Streamable HTTP endpoint of Berri LiteLLM, the widely used LLM gateway and proxy. Scored CVSS 8.8 and added to CISA’s KEV catalog on 2 September 2026, it allows an unauthenticated attacker to establish an authenticated MCP session using an arbitrary bearer token — the endpoint accepts the token rather than validating it. Reporting describes honeypot detections of exploitation aimed at model enumeration endpoints, which is the reconnaissance step before abuse of the gateway itself. This is the first KEV entry to name an MCP implementation, and the shape of the risk is specific to what a model gateway is for. Where MCP tooling is wired into internal systems, an authenticated session may also reach whatever those tools can reach, which is a considerably larger problem than an inflated model bill.
