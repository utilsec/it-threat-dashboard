Top Story

GitLab’s maximum-severity path traversal went from patch to confirmed in-the-wild exploitation in three days — and what a single request reads is your CI/CD secrets

GitLab disclosed and patched CVE-2026-85706 on 11 September: an unauthenticated path traversal in the repository commits interface of self-managed GitLab CE and EE, scored CVSS 10.0, that lets anyone who can reach the instance read arbitrary files from the server in one HTTP request. Any instance hosting at least one public project is reachable without credentials. watchTowr Labs and CISA both reported internet-wide scanning and probing beginning almost immediately after disclosure, and on 14 September CISA and GitLab confirmed exploitation in the wild; the flaw was added to the Known Exploited Vulnerabilities catalog on 11–12 September with a federal civilian remediation deadline of 14 September. Affected builds run from 18.7 through 19.1.8, 19.2 and 19.3 before the fix; patched releases are 19.1.8, 19.2.6 and 19.3.2. GitLab.com SaaS customers were not affected, so the entire exposure is self-hosted. It leads this edition because of what the primitive actually buys an attacker: not code execution, but unauthenticated read of whatever the GitLab service account can see — configuration files, the secrets file, CI/CD variables, registry and cloud credentials, deploy keys and signing material. In a technology or SaaS organisation that is the shortest available path from an internet-facing web request to the build pipeline that ships your product to customers, which is why an arbitrary-file-read bug deserves to be treated as a supply-chain incident rather than an information-disclosure one. The three days between the fix and confirmed exploitation is the number worth carrying into your own patch SLA.

A three-zero-day chain against Chrome and Windows delivered the GRIMWEDGE backdoor through a compromised university site — and it ran in the gap between the Chromium fix and the Chrome release

Researchers disclosed on 15 September a campaign active since 1 September in which spear-phishing links routed victims through a compromised US university website — abused via reflected cross-site scripting purely as attack infrastructure — into an exploit chain combining CVE-2026-85046 and CVE-2026-87491 in Chrome’s V8 engine and sandbox with CVE-2026-85880, the Windows ALPC elevation-of-privilege flaw Microsoft patched this month. The payloads are a multi-stage JavaScript backdoor tracked as GRIMWEDGE, capable of reconnaissance, file and process management and command execution, and a credential stealer tracked as LONGTALE. Attribution to China-linked UTA0560, also tracked as JungleBamboo and associated with APT31, is researcher-assessed rather than official. The intended victims were NGOs, but the detail that matters to every technology organisation is the timing: the operators worked inside a “patch gap”, exploiting bugs whose fixes were already visible in the open-source Chromium tree but had not yet shipped in stable Chrome. CVE-2026-87491 was Chrome’s seventh in-the-wild zero-day of 2026 and was fixed on 9 September in Chrome 153.0.8010.36/.37. Browser patching on a monthly cadence, or on whatever cadence the fleet happens to drift to, is not fast enough against an actor reading the same commit history your vendor does.

“Red Heron” industrialised a public Gitea exploit into a scanner and took repositories from 13 organisations — every one of them running a patch that had been available since July

The actor scanned 1,386 Gitea instances across seven countries and confirmed compromises at 13 organisations in the United States, Taiwan, Canada, Argentina, Qatar and Sri Lanka, spanning defence, elections, energy, aerospace, telecommunications and government. A two-month-old patched CVE remained a viable mass-compromise route because nobody owned the instances.

Medium Supply Chain

A browser extension with about 31,000 installs quietly forwarded OAuth tokens to a Russian proxy — the enterprise exposure is not Twitch, it is the extension model

Researchers reported on 14 September that an extension distributed across browser stores as “Twitch Enhanced Viewer” and “JeetBot”, with roughly 30,000 to 31,000 installs, harvested users’ session and OAuth tokens and exfiltrated them to proxy infrastructure belonging to a Russian commercial bot service. The direct victim population is consumer, and no enterprise breach has been tied to it. It earns a place here because of the mechanism rather than the brand: a browser extension runs inside the authenticated session of every site the user visits, and an extension installed on a corporate or bring-your-own device can read or replay tokens for the SaaS applications the same browser is signed into. Token theft is the quiet form of account takeover, because a stolen session cookie or OAuth token presents as a legitimate, already-authenticated user and does not trigger a second-factor prompt. Most organisations run no extension policy at all, which means the control surface for this class of risk is currently the individual employee’s judgement in a store listing.

The ScreenConnect flaw now has a CVE, a patch and a three-day federal deadline — and the exploitation pattern is worm-like, spreading from support sessions into the estates behind them

What this page carried last week as an unpatched ConnectWise disclosure has resolved into CVE-2026-84869, a CVSS 9.9 missing-authorization and improper-privilege-management flaw in ScreenConnect. ConnectWise has confirmed exploitation, which researchers trace back to 20 August, and CISA added the CVE to the Known Exploited Vulnerabilities catalog on 12 September under Binding Operational Directive 26-04, giving federal civilian agencies three days to remediate. The mechanics are what earn the “worm-like” description: attackers abuse legitimate remote-support sessions to transfer and execute files without host confirmation, then use social engineering to get victims to run modified ScreenConnect clients that detect other active sessions and push VBScript payloads to the machines connected to them. Version 26.6.5 contains the fix; disabling the TransferFiles permission is the interim mitigation. For a technology or managed-service organisation the exposure runs in both directions, and that has not changed: an affected instance reaches into customer environments that never installed the product, and if you are the customer, your provider’s patch timeline is your patch timeline.

The Artifactory story this page opened at the end of August with CVE-2026-82329, a CVSS 9.8 improper-authentication flaw that let an unauthenticated attacker reach administrative privileges under a default configuration, has developed into something more deliberate. Reporting on 11 and 14 September describes attackers chaining CVE-2026-42018, a token-disclosure flaw that yields an internal anonymous-user JWT even where anonymous access has been disabled, into CVE-2026-42016, an insufficient token-validation issue used to escalate to administrator — in some observed cases in under five minutes — before deploying a custom Rust-based command-and-control backdoor. Artifactory sits in the middle of the build chain for a great many software vendors, holding registry credentials, signing material and the packages that ship to customers; fixed builds start at 7.111.21 depending on branch, and JFrog’s cloud instances were already remediated, so the exposure is self-hosted.

Reporting on 8 September describes compromises of F5 BIG-IP Access Policy Manager devices in which attackers install a Linux rootkit that hooks PHP file loading and injects a web shell directly into memory. Treat any affected device as a credential-exposure event: rebuild it rather than clean it, and rotate what passed through it.

Claimed, not confirmed: a researcher’s FalconFlank proof of concept turns a CrowdStrike Falcon remediation feature into SYSTEM

A researcher using the handle Nightmare Eclipse published a proof of concept on 4 September 2026 for what they call FalconFlank, a claimed local privilege escalation in the CrowdStrike Falcon sensor. The technique abuses the sensor’s Microsoft Office suspicious-macro remediation function to spawn a command prompt running as SYSTEM, on Windows 11 25H2 and Windows Server 2025. Treat the status carefully, because the distinction is the story: no CVE identifier has been assigned, and no in-the-wild exploitation has been reported. CrowdStrike has said it is actively investigating the claims, has advised customers to disable the Microsoft Office File Suspicious Macro Removal policy setting as a precaution, and notes that customers remain protected through the Cloud Anti-malware for Microsoft Office Files settings. The researcher stated they expected CrowdStrike to have detections in place by the time the proof of concept was released. What earns it a place here is the pattern rather than the severity — this is a local escalation, not a remote compromise, and it requires code execution on the host first. Security agents run with the highest privilege on every endpoint a technology company owns, which makes their own remediation features an attractive place to look.
