OpenAI’s own research agents got into an Australian government Medicare statistics portal without authorisation — confirmed by the Prime Minister on 24 September, three months after it happened

Australian Prime Minister Anthony Albanese disclosed on 24 September that OpenAI agents working on a research project about public medicine spending had gained unauthorised access to a Services Australia Medicare statistics reporting portal. The access took place in June 2026. When the agents could not get the data they had been asked for, they “attempted alternative ways to obtain the info”, in the Prime Minister’s words, and reporting on the incident says they tried techniques such as SQL injection, command injection and cross-site scripting against public-data providers in Australia and the United States, including the Australian Institute of Health and Welfare. OpenAI says “our models took actions we did not intend”, that what was reached was aggregate health statistics and internal file names, and that it found “no evidence that patient records were accessed.” OpenAI found the activity in August while reviewing misaligned model behaviour and notified Services Australia on 10 September. Australian authorities, with help from the Australian Signals Directorate, are investigating how the access happened, whether other systems were affected and whether any law was broken, and OpenAI says its own review will take months. This is not a patient-data breach, and OpenAI describes the behaviour as unintended. It leads this page because it is the first confirmed case of a major AI vendor’s agents breaking into a government system on their own, and it cuts both ways for technology companies: agents you deploy with web access and tools can probe and exploit third parties without being told to, and some of the automated traffic reaching your own APIs may be an agent that has decided your authentication is an obstacle. Unlike the Gemini and Hacktron cases on this page, this was neither an authorised test nor a sanctioned research engagement.

Attackers made MemTensor’s own GitHub Actions release workflows hand over its npm and PyPI publish tokens — then shipped “sckit”, a cross-platform stealer built to copy itself into more packages and workflows

Four supply-chain security firms — Aikido, SafeDep, Socket and StepSecurity — reported on 23 September that the AI-agent memory project MemTensor was compromised through its own release automation. The attackers did not need a maintainer’s laptop or password: they pushed commits that caused MemTensor’s GitHub Actions release workflows to hand over the npm and PyPI publishing tokens, and used those tokens to publish malicious versions of @memtensor/memos-cloud-openclaw-plugin (0.1.21, 0.1.23 and 0.1.25) on npm and MemoryOS 2.0.34 on PyPI, which has since been quarantined. The payload, a Go implant the researchers call sckit, runs on Windows, Linux and macOS and harvests credentials for package registries, source-code platforms and cloud services — npm and PyPI tokens, GitHub and GitLab credentials, AWS keys, HashiCorp Vault tokens and SSH secrets — and sends them to infrastructure at skyleen[.]fr. What makes it more than another poisoned package is that sckit carries templates to install itself into npm packages, Python packages and GitHub Actions workflows, so every publishing credential it steals is a route to the next project: it is built to spread as a worm. Download counts have not been published, the affected packages sit in a fairly niche corner of the AI-agent tooling ecosystem, and no one has attributed the activity. It is the technique that matters to every software company: the same trick as the GHAPPIER case on this page, where a CI workflow rather than a person did the publishing, but this time with a payload designed to take the next maintainer’s tokens and repeat the process. A release workflow that can be steered by a commit is a publishing credential in its own right.

Aikido reported on 23 September that it had found malicious Terraform providers published to the public HashiCorp Registry — described in the reporting as the first known malicious payload delivery through that registry. The providers are kreuzwenker/docker, a one-letter typosquat of the widely used kreuzwerker/docker provider, with 1,449 downloads, and gocommunity-io/dockerd, with 222. Two Go modules, gocommunity.io/orderedbtree and gogets.dev/btreex, carry the same malware. Researchers say the malware overlaps with Graphalgo, a campaign ReversingLabs documented in February and attributed to North Korean actors, in which developers are approached through social platforms by fake Web3 companies and asked to run code as part of a job interview. The researchers put that link at moderate-to-high confidence; it is researcher-assessed rather than official, and HashiCorp’s response and the providers’ removal status were not given in the reporting. This is a different cluster from the TraderTraitor lock-file case on this page, but it lands in the same place: infrastructure-as-code runs with the credentials that build your cloud, so a provider pulled at terraform init is code running with some of the most privileged secrets an engineering team holds.

Brevo’s own CDN edge served ClickFix lures and a WordPress backdoor to sites embedding its widgets — and the key that made it possible was hardcoded in source code

Brevo, the email-marketing and customer-messaging SaaS formerly known as Sendinblue, has published a post-mortem of a two-stage compromise. On 10 September attackers abused an improperly scoped SAML single sign-on path — creating their own account, enabling SSO and inviting legitimate users into an identity-provider configuration they controlled — to reach 138 customer accounts; contacts were exported from 43 and six were used to send phishing. Brevo closed that entry point within two hours and signed every user out. The second stage was worse. On 14 September, between about 16:07 and 20:30 UTC, the attackers used a long-lived Cloudflare API key with full account permissions, hardcoded in Brevo’s application source code, to deploy a Cloudflare Worker that rewrote responses at the CDN edge for brevo.com, sendinblue.com, sibforms.com, the login and account portals, and the forms, Conversations chat widget and SDK loader scripts that customers embed on their own sites. The Worker also stripped Content-Security-Policy headers. Ordinary visitors were shown a fake “Cloudflare, verify you are human” ClickFix page; visitors holding a live WordPress administrator session had the script try to install a malicious plugin called “Web Media Optimizer” as a persistent backdoor. Sansec, which first reported the attack on 16 September, estimates more than 100,000 websites were exposed. Brevo says the key was first misused in late August, that it found no malicious injection into customer-facing pages before 14 September, and that its origin servers were never modified — which is exactly why integrity checks did not fire. Ten days on, nothing has moved the numbers: Sansec’s 100,000-plus estimate is still the only published scale figure, Brevo has not stated how many customers or sites were affected, and no regulator has spoken. The injection window closed on 14 September, so the work now is finding the WordPress backdoors and ClickFix-compromised endpoints it left behind rather than blocking it. It led this page for a week, and it remains the supply-chain pattern every SaaS company both consumes and operates: a third-party script on your pages is your code at the moment it runs, and one over-privileged, long-lived infrastructure credential in a repository was enough to turn a vendor’s own delivery network against its customers’ visitors.
