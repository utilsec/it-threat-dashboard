JetBrains left one TeamCity server unpatched for a month after it entered CISA KEV — attackers took AWS credentials and, possibly, customer source code

JetBrains has concluded its investigation into a compromise of Cadence, the cloud compute service that runs workloads for PyCharm users. The entry point was CVE-2026-63077, a critical deserialization flaw in TeamCity (CVSS 9.8) that lets an unauthenticated attacker with network access to a TeamCity server bypass authentication and run operating-system commands. It was disclosed in July 2026 and CISA added it to the Known Exploited Vulnerabilities catalog on 5 August. The Cadence environment used TeamCity to orchestrate its workloads, and that server was still vulnerable when intruder activity began on 8 August. JetBrains detected the compromise on 23 August, took the server offline on 24 August, and published its conclusions on 3 September; the company acknowledged the server should have been patched without explaining the delay. What the attacker reached is the uncomfortable part. A complete 2024 server backup was taken, containing usernames, real names, email addresses, login timestamps and IP addresses, along with credentials and configuration data. AWS IAM credentials and secrets were exposed, and with them contents of S3 buckets in JetBrains AWS accounts, plus configuration files, artifacts and logs. JetBrains says source code and project files synchronised to Cadence during the window may also have been accessed, and it has invalidated all Cadence plugin access tokens. It says its findings did not identify affected users beyond those already contacted directly. This leads the sector because it is the ordinary version of a supply-chain failure: not a novel technique, but a known-exploited CVE in a build orchestrator that sat unpatched inside a software vendor for weeks while it held the keys to a cloud estate and other people’s code.

Critical Zero-day

An unpatched Magento and Adobe Commerce zero-day is backdooring stores now, and Adobe has published nothing

Sansec disclosed on 5 September 2026 a zero-day it calls StyleSmuggler: unauthenticated remote code execution against Magento Open Source and Adobe Commerce, with attacks observed beginning 4 September. The chain is two-stage and unusually quiet. The attacker first gets malicious PHP written into files Magento produces during normal operation, such as failure reports, then reaches execution through the platform’s Payment Transaction Failed Reminder function — the code runs while Magento renders the message, so nobody has to open anything. Execution abuses dependency-injection code scanners to load attacker-controlled file paths, and the payload observed is a persistent Rust-based backdoor. Sansec reports all current versions as vulnerable, with confirmed compromises on Magento Open Source 2.4.7, 2.4.8 and 2.4.9, and at least one victim running 2.4.6-p15 with the latest official patches applied. As of 6 September Adobe had issued no advisory, no CVE identifier, no patch and no official workaround; the vendor’s next scheduled security release was 8 September, with no confirmation it addresses this. Technology teams that do not think of themselves as retail should still check — Magento sits behind a great many agency-managed and white-label storefronts, and hosting providers and MSPs carry the operational exposure for customers who have never heard of the platform they are running on.

Critical Supply Chain

A 33-hour BGP hijack pointed Softaculous update traffic at an impostor, which shipped a backdoored Virtualizor package

Softaculous has confirmed that between 20:57 UTC on 28 August and 06:10 UTC on 30 August 2026 an unauthorised, more-specific BGP announcement for its 162.55.80.0/24 block diverted traffic bound for its update systems and customer portal. The vendor attributes the announcement to AS62390 (NexonHost) carried through transit provider AS6204 (Zet.net). The detail that makes this worth reading twice is the certificate: because Let’s Encrypt’s automated domain-ownership validation was itself routed through the hijack, the attacker obtained a valid TLS certificate for the hostname, so clients saw no warning and no name mismatch. Softaculous says a malicious Virtualizor update package was delivered to a small number of installations — a handful of servers rather than the general user base — and that update packages carried no cryptographic verification at the time, so a modified package would not have been rejected on that basis. The malicious update installed a systemd unit at /etc/systemd/system/java-jre-update.service for persistent root access. Softaculous shipped 3.2.9.9 on 1 September with a Security Analyzer script and says it has begun implementing code signing. For hosting providers and MSPs the lesson is uncomfortable: TLS and a trusted vendor hostname verified nothing here, because routing decided who the hostname resolved to.

Critical Supply Chain

Coder’s module registry served credential-stealing Terraform modules for fourteen hours after its Cloudflare infrastructure was hijacked

On 31 August 2026, between roughly 07:35 and 21:45 UTC, some requests to Coder’s public module registry were answered by servers the attacker controlled rather than by Coder. The access was not to the registry application itself: an unidentified actor reached Coder’s Cloudflare infrastructure and added their own IP addresses to the pool the legitimate registry hostname resolved into, so a share of traffic was silently steered away. The modules returned were Terraform code that behaved as an information stealer, sweeping environment variables and secrets, cloud and AI provider API keys, CI/CD credentials, SSH keys and authentication tokens, database passwords and configuration data, and sending them to the lookalike domain coder-infra[.]com. Coder shipped fixed releases 2.37.0, 2.36.4, 2.35.7 and 2.34.9 and said refresh tokens were not passed to the provisioner and that it has seen no evidence of impact to customer data it holds. That is a narrower statement than “no one lost secrets” — anything already present in a workspace environment during that window was in scope. Coder’s published customer list includes Dropbox, Palantir, Square, Mercedes-Benz and US government agencies, which is a measure of blast radius rather than a victim list. The pattern to take away is that the registry was never breached; the name resolution in front of it was, and module consumers had no way to tell.

Forged Artifactory admin tokens survive the patch, so upgrading alone does not evict the attacker

Last week’s lead story stays on the board because its remediation is not finished by patching. JFrog disclosed and fixed CVE-2026-82329 on 28 August 2026, an improper-authentication flaw (CVSS 9.8) letting an unauthenticated attacker with network access to a self-managed Artifactory instance in its default configuration forge administrative tokens. Proof-of-concept code appeared within a day; watchTowr reported live exploitation from 31 August, with attackers minting admin tokens and then enumerating users, groups, credential sets and federated access topologies from several IP addresses in different geographies. The activity was characterised as targeted rather than mass scanning. CISA added the CVE to KEV on 2 September with a 5 September federal deadline — the second Artifactory entry in the catalog inside a week, after the CVE-2026-66384 Docker cache path traversal added on 27 August with a 10 September date. Artifactory sits between a build pipeline and everything it ships, and Dark Reading notes roughly 83% of the Fortune 100 run it, so admin there means the ability to replace or poison artifacts that downstream consumers trust implicitly.

High Incident

About 5,000 Dropbox accounts were entered with no password, because a Lenovo ID could be registered on someone else’s email

Dropbox disclosed on 2 September 2026 that roughly 5,000 accounts were accessed without authorisation between 4 and 21 August. There was no breach of Dropbox systems and no credential stuffing. The weakness was in the seam between two identity systems: Lenovo’s email verification process allowed an attacker to register a Lenovo ID using an email address they did not control, and Dropbox’s account-linking trusted that Lenovo ID as proof of the address without asking for further confirmation. Signing in through the Lenovo identity provider then produced access to the matching Dropbox account without ever presenting the Dropbox password. Some affected users had never had a Lenovo account at all; only their email address was needed. Lenovo says a legacy integration was involved and that its own customers were not affected, and that the two companies worked together to mitigate the risk. Dropbox expired every session that had authenticated through a Lenovo ID and now requires a password alongside Lenovo ID authentication. Any SaaS product that lets a user link a third-party identity to an existing account by matching email addresses has the same failure mode, and it is worth checking which of your own federation and social-login paths treat an asserted email address as verified.

Dropbox — unauthorised access 4–21 Aug 2026, approx. 5,000 accounts
Confirmed abuse — accounts accessed via a third-party identity provider, not a Dropbox system breach Identity integration flaw, not a CVE — not in CISA KEV
Mitigated — Lenovo ID sessions expired; Dropbox now requires a password with Lenovo ID sign-in Action: As a customer: check whether corporate Dropbox accounts have third-party identity providers linked, unlink any you did not intentionally enable, review sign-in history for 4–21 August, and enforce SSO through your own identity provider with MFA rather than allowing consumer identity linking. As a vendor: audit your own account-linking logic for the same assumption — an email claim from a federated provider is not proof of address ownership unless you verify it yourself, and linking an external identity to an existing account should always require authentication with the existing credential first.

High Research

A repository’s own git config can make an AI coding agent run the attacker’s command before you type anything

Manifold Security published research on 3 September 2026 describing a class of flaw it calls GitSpawn, affecting several AI coding agents. The agents run git commands at start-up to gather repository context, and they inherit the repository’s .git/config without sanitising it. Git’s core.fsmonitor setting names a helper program that git executes whenever it refreshes the index, including during ordinary commands such as git status or git diff — so a repository can specify an arbitrary command and the agent will run it with no user interaction. Execution happens as the developer, outside any agent sandbox, reaching SSH keys, cloud credentials, shell tokens and every other local repository; in some agents it occurs before the workspace-trust prompt, and in at least one before authentication. The mitigating detail is the delivery path: cloning or fetching a hostile repository is not enough, because .git/config is not transferred. The repository has to arrive as files — a zip, a shared drive, an archive from a candidate or a contractor, a USB stick. At publication Manifold listed fixes shipped for Claude Code (2.1.196), Goose 1.44.0 (CVE-2026-72718), OpenAI Codex and Cursor, with Hermes (CVE-2026-71963), Qwen Code and Grok Build still unpatched. The general defence for vendors is to invoke git with configuration explicitly neutralised, for example git -c core.fsmonitor=false.

Treat agent execution as running with the developer’s full identity, because it does: keep long-lived cloud keys off developer machines, scope tokens tightly, and require a dedicated container or VM for untrusted code review. If you build agent tooling yourself, sanitise git configuration at invocation rather than trusting the repository.

High Research

One leaked AWS key turned into a resold Bedrock inference business billed to the victim

FortiGuard Labs published an intrusion analysis on 3 September 2026 in which a single long-lived AWS IAM access key carrying AdministratorAccess was used to monetise the victim’s account rather than to steal its data. The sequence is worth memorising because it is quiet at every step. The actor created new IAM users for persistence, then subscribed to foundation models through AWS Marketplace using CreateAgreementRequest and AcceptAgreementRequest, which is an unremarkable API pair in most environments. They then generated Bedrock service-specific API keys, giving a second and less conspicuous path to invoke models, and ran inference at volume. The bill lands on the victim: Fortinet puts sustained abuse of premium foundation models above 46,000 US dollars a day, rising past 100,000 dollars a day at the top of the model range. Two structural weaknesses make this work. Bedrock invocation logging is off by default, so the activity leaves little trace unless someone turned it on in advance. And a static administrator key is still a common artefact in CI systems, scripts and developer laptops, where it never expires and rarely gets reviewed. For SaaS and cloud teams the practical exposure is that AI spend is now a monetisable asset in its own right, and it is metered by the second.

Medium Research

Someone spent a month quietly guessing AWS root passwords at more than 150 organisations, two tries at a time

Datadog Security Labs reported on 31 August 2026 a password-spraying campaign aimed specifically at AWS root user accounts across more than 150 organisations between 24 July and 23 August. The restraint is the interesting part. The median targeted organisation saw only two failed sign-in attempts across the whole month, with the busiest seeing about eight — low enough to stay under lockout thresholds and under most alerting. Requests came from distributed proxy infrastructure spread across countries and autonomous systems, with spoofed user agents including one presenting as Microsoft Edge built on Chrome 85 and another as Firefox 120. Victims spanned industries and countries with no obvious sector pattern, which suggests the operator was working from a list of root account email addresses assembled from leaks, phishing or reconnaissance rather than choosing targets. Datadog identified no successful authentications, so there is no evidence any account was taken. The reason to care anyway is that the root user sits outside most of the controls organisations rely on — it ignores IAM policies, and in many estates it is the one identity nobody has looked at since the account was opened. AWS has enforced MFA for root users on management accounts since June 2025, which is what makes a campaign like this expensive rather than productive.

A NetScaler authentication bypass patched in August is now drawing exploit attempts, with 22,000 appliances visible online

High Advisory

A twelve-year-old PostgreSQL logical decoding flaw lets a replication account run code as the database OS user

PostgreSQL shipped fixes on 4 September 2026 for CVE-2026-6471 (CVSS 7.2), nicknamed PostGREShell by Cyera Research and reported by Vladimir Tokarev and Yu Kunpeng. Where wal_level is set to logical, an account holding the REPLICATION attribute could nominate any loadable library as a logical decoding output plugin, bypassing PostgreSQL’s usual path restrictions through the replication protocol and executing code as the operating-system user the database runs as. The weakness has existed since logical decoding arrived in PostgreSQL 9.4 in 2014. Fixed releases are 18.6, 17.11, 16.15, 15.19 and 14.24, and the fix introduces a new output_plugin_libraries parameter defaulting to pgoutput, test_decoding. Exploitation is not trivial — it needs replication credentials plus a way to point at a library, which on Windows means SMB access to an attacker-controlled share and on Linux or macOS means NFS automounting or an existing file-write primitive. There was no public proof of concept and no KEV listing as of 4 September. It matters to this sector because logical replication is how change-data-capture pipelines, analytics warehouses and multi-region SaaS architectures move data, so REPLICATION-attributed accounts are widespread, often shared between systems, and frequently older than the people administering them.

Regulation & Policy
Medium Policy

From 11 September, EU software vendors have 24 hours to report an actively exploited vulnerability in their own product

Article 14 of the EU Cyber Resilience Act takes effect on 11 September 2026, more than a year ahead of the regulation’s general application on 11 December 2027. From that date, manufacturers of products with digital elements must notify the CSIRT of the member state where they are established, with the notification shared simultaneously with ENISA, whenever they become aware of an actively exploited vulnerability in their product or of a severe incident affecting the product’s security. The clock is staged: an early warning within 24 hours of becoming aware, a fuller notification within 72 hours, and a final report within 14 days of a corrective measure being available for a vulnerability, or within one month for a severe incident. Reporting goes through the CRA Single Reporting Platform so a manufacturer files once. Several details determine how much work this actually is. The duty applies even after a product is no longer supported. There is no retroactive obligation for vulnerabilities known before 11 September. A vulnerability in a third-party component is reportable only where it is exploitable within your product, which puts weight on knowing your dependency graph well enough to make that call inside a day. And manufacturers must inform affected users proportionately, without necessarily publishing technical detail. In practice the requirement is an internal one: the path from a support ticket or a researcher email to a filed notification has to be fast enough to survive a 24-hour deadline.

Write the 24-hour decision procedure now: what counts as “aware”, who decides whether a component flaw is exploitable in your product, and who approves customer communication. Rehearse it against a recent real advisory. Make sure the dependency inventory can answer “is this exploitable in our product” within hours, and check that the duty is covered for products you no longer support but that remain in the field.
